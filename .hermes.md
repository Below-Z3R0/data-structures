# .hermes.md — nextjs-template (capa agente)

> Este archivo es para la IA que trabaja en un proyecto creado desde este
> template. NO es documentación para la persona usuaria: eso vive en
> `README.md`.
>
> Si buscás reglas de comportamiento general del agente, están en
> `~/.hermes/profiles/coding/SOUL.md`. Acá van las reglas **de este proyecto**.

## Como usar este archivo

1. Leer completo antes de tocar código.
2. Responder las [preguntas iniciales](#preguntas-iniciales-obligatorias)
   antes de escribir la primera línea de un proyecto nuevo.
3. Aplicar las reglas de cada sistema al momento de modificarlo.
4. Ante la duda, la regla escrita acá gana sobre la costumbre.

## Las dos capas de un proyecto

Un proyecto creado desde este template tiene **dos carpetas**:

```
Mi-Proyecto/          ← CAPA AGENTE (primera letra MAYÚSCULA)
├── .hermes.md        ← este archivo: reglas operativas para la IA
├── AGENTS.md         ← entry point para agentes
├── README.md         ← docs para humanos
├── CHANGELOG.md      ← historial
├── .scratch/         ← temporales de la IA (nunca en la carpeta de código)
└── mi-proyecto/      ← CAPA CÓDIGO (siempre en minúscula)
    ├── src/
    ├── docs/
    ├── public/
    ├── package.json
    └── biome.json
```

| Capa   | Regla                       | Qué contiene                                                         |
| ------ | --------------------------- | -------------------------------------------------------------------- |
| Agente | Primera letra **MAYÚSCULA** | `.hermes.md`, `AGENTS.md`, `README.md`, `CHANGELOG.md`, `.scratch/`  |
| Código | **minúscula**               | `src/`, `docs/`, `public/`, `package.json`, `biome.json`, `bun.lock` |

Reglas de la separación:

- La carpeta de código **nunca** lleva archivos de agente. Nada de `.hermes.md`,
  `AGENTS.md` ni `README.md` adentro de `src/` ni en la raíz de la carpeta de
  código.
- El output de **Graphify** va en `docs/graphify/` **dentro de la carpeta de
  código**, nunca en la capa agente. Es generado y no se trackea en git.
- El `package.json` vive **solo** en la carpeta de código. El root del proyecto
  no tiene dependencias.
- `node_modules` queda en la carpeta de código, no en el root.

Este template en sí es la carpeta de código pura: cuando clones el template y
crees el proyecto, lo que hoy es la raíz del template pasa a ser la carpeta en
minúscula dentro de tu proyecto.

## Preguntas iniciales obligatorias

**Antes de escribir código** en un proyecto nuevo, hay que responder estas
cinco preguntas. El template se personaliza según el tipo de proyecto: un
template listo desde el inicio acelera el trabajo y evita rehacer la base.

| #   | Pregunta                                                                      | Qué decide                                                                                                                                                                                 |
| --- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | ¿El proyecto usa **Supabase** como backend o **data estática** en JSON local? | Si es estático, se borra `src/services/supabase/` y se genera el JSON con el contenido real. Si es Supabase, se corre `setup-database.sql` y se configuran las credenciales.               |
| 2   | ¿Tiene **i18n**? ¿Qué idiomas?                                                | Si no tiene, se simplifica el schema de traducciones y se deja un solo idioma. Si tiene, se definen los `lang_code` en la tabla `languages` y un JSON por idioma.                          |
| 3   | ¿Cuáles son las **paletas** del tema?                                         | Se eligen entre las 4 del template (`.light`, `.dark`, `.rosepine-dark`, `.rosepine-light`) o se personalize el set. Cada paleta nueva tiene que definirse en las 4 (o en las que queden). |
| 4   | ¿Tiene **autenticación** o **panel de administración**?                       | Si sí, se mantiene el route group `(admin)` con su control de rol. Si no, se borran `src/app/(admin)/`, `src/app/login/`, `src/app/auth/` y el middleware.                                 |
| 5   | ¿Qué **módulos o sistemas** hay que documentar en `docs/`?                    | Define qué carpetas de `docs/` se crean. Cada módulo del sistema lleva su carpeta con su `README.md` índice.                                                                               |

Hacé las preguntas **antes** de arrancar, no después. Un template
personalizado desde el principio es más barato que uno genérico que hay que
adaptar sobre la marcha.

## Stack obligatorio

| Pieza           | Elección                                                 | Prohibido                    |
| --------------- | -------------------------------------------------------- | ---------------------------- |
| Package manager | **Bun** (`bun install`, `bun run dev`, `bun.lock`)       | npm, pnpm, yarn              |
| Lint + format   | **Biome** (`bunx biome check --write`)                   | ESLint, Prettier             |
| CSS             | **Tailwind v4** con `@theme` como única fuente de verdad | CSS hardcoded en componentes |
| Temas           | **next-themes** con `attribute="class"`                  | scripts propios de tema      |
| Animaciones     | **Motion** importando de `motion/react`                  | framer-motion                |
| Validación      | **Zod** en el borde (datos que entran al sistema)        | validación manual            |
| Tipos           | **TypeScript estricto** (`strict: true`)                 | `any` para silenciar errores |

### Bun

El `package.json` declara `packageManager: bun@1.4.4` y el lockfile es
`bun.lock`. **No** generes `package-lock.json` ni `pnpm-lock.yaml`.

Si `bun` no está en el PATH (shells no-login), usá la ruta absoluta:

```bash
~/.bun/bin/bun install
~/.bun/bin/bun run dev
```

### Biome

Biome corre con los dominios de Next y React activados. El `biome.json` ignora
`docs/graphify` (contenido generado).

```bash
bun run lint     # biome check
bun run format   # biome format --write
```

## Theming v2

El sistema de temas vive en `src/app/globals.css` y tiene **4 paletas** con
**45 variables CSS cada una** (las mismas 45 en las cuatro).

| Paleta            | Origen   | Descripción                 |
| ----------------- | -------- | --------------------------- |
| `.dark`           | Default  | Violeta oscuro, fondo negro |
| `.light`          | Default  | Violeta claro, fondo blanco |
| `.rosepine-dark`  | Noctalia | Rosepine main               |
| `.rosepine-light` | Noctalia | Rosepine Dawn               |

Las variables están agrupadas por familia semántica: backgrounds, brand,
estructura, muted, accent, semánticos, bordes, interacción, texto,
highlighters y la familia de Rosepine (`love`, `pine`, `foam`, `iris`).

### Cómo agregar una variable nueva

1. Definir el valor en las **4 paletas**. Si falta en una, esa paleta hereda el
   valor de otra y el sistema se rompe.
2. Exponerla en `@theme` como `--color-<nombre>: var(--<nombre>);`.
3. Documentarla en `src/components/hooks/theming.v2.ts` (tipo `ThemeToken`).

Ese archivo es documentación ejecutable: los tipos están sincronizados con el
CSS y `ALL_TAILWIND_UTILITIES` lista las utilities válidas.

### Selectores de paleta

Las paletas se definen con **selectores de clase directa** (`.dark { ... }`).
`next-themes` con `attribute="class"` pone la clase en `<html>`, y las
variables heredan al `body`.

Cuando necesites aplicar variables a un subárbol **sin** pisar las utilities
de Tailwind, usá `:where()`: tiene especificidad 0 y deja que las utilities
ganen.

```css
/* Bien: especificidad 0, no pisa nada */
:where(.dark, .dark body) { ... }

/* Mal: especificidad alta, pisa reglas posteriores */
.dark body { ... }
```

### Reglas de uso

- `text-primary-foreground` es SIEMPRE `#fff` en `.dark`, `.light` y
  `.rosepine-light`. En `.rosepine-dark` es `#191724` porque el `primary` de
  Rosepine es claro (`#ebbcba`) y necesita texto oscuro encima. La regla real
  es: **nunca hardcodear el color**, usar siempre el token.
- `text-foreground` para texto normal, `text-muted-foreground` para texto
  secundario. Nunca `text-background`.
- Bordes: `border border-border` (ancho + color juntos), nunca `border` solo.
- El layout monta el `ThemeProvider` con `disableTransitionOnChange`: sin eso,
  cambiar de paleta anima todas las transiciones y se ve un barrido.

### Clases que NO existen (y por qué importan)

Estas no están definidas en el `@theme`. Usarlas compila pero no hace nada, y
el error es silencioso:

| No usar                     | Usar en su lugar                                  |
| --------------------------- | ------------------------------------------------- |
| `text-background`           | `text-foreground` o `text-primary-foreground`     |
| `bg-border`                 | `bg-muted`                                        |
| `text-body`                 | `text-muted-foreground`                           |
| `text-wrap: balance`        | `text-wrap-balance` (sin espacio, es una utility) |
| `border bordear-subtle`     | `border`                                          |
| `text-white` hardcoded      | `text-primary-foreground`                         |
| `bg-slate-900/50` hardcoded | `bg-popover`                                      |

Y estas dos que son errores de forma, no de nombre:

- `border border border-glow` → `border border-glow` (triple borde).
- `transition: all` → nunca. Con `next-themes` hace que cambiar de paleta
  anime todas las propiedades. `disableTransitionOnChange` lo resuelve para
  el cambio de tema; para el resto, transition explícita de la propiedad que
  quieras animar.

## Motion

Animaciones con `motion` (v14), importando de `motion/react`.

- El layout raíz envuelve todo en `<LazyMotion features={domAnimation} strict>`.
  Con `strict` tenés que usar `m`, no `motion`. Usar `motion.div` adentro de
  `LazyMotion strict` rompe el build.
- `m` pesa 4.6 KB contra los 30 KB del bundle completo. No lo cambies por
  `motion`.
- **NUNCA** loops infinitos de animación, salvo que estén controlados por
  `isLoading`.
- **NUNCA** `IntersectionObserver` manual: usá `whileInView`.
- Animaciones de entrada: siempre `viewport={{ once: true }}`. Sin eso, la
  animación se repite cada vez que el elemento entra y sale del viewport.
- `AnimatePresence` para animaciones de salida (modales, toasts). Sin él, el
  elemento desaparece de golpe.
- Las variantes se definen a nivel de módulo, no inline en cada componente.
- `StaggerItem` no define `initial` ni `whileInView`: hereda las variantes del
  padre. Ponerle `initial="hidden"` a mano rompe la orquestación.

Las primitivas disponibles están en `src/components/animations/Animations.tsx`:
`SectionReveal`, `TextReveal`, `SlideReveal`, `StaggerGroup`, `StaggerItem`,
`EyebrowReveal`, `PopReveal`, `ExpandLine`, `LoadingDots`.

## Atomic design estricto

Tres niveles, una sola dirección de dependencia:

```
organisms  ->  molecules  ->  atoms
```

Nunca al revés. Un atom nunca importa una molecule.

| Nivel        | Qué es                                          | Qué NO hace                                        |
| ------------ | ----------------------------------------------- | -------------------------------------------------- |
| `atoms/`     | Primitivas visuales sin lógica de negocio       | No conocen el dominio, no reciben datos de la base |
| `molecules/` | Composiciones de atoms con estado o interacción | No hacen fetch                                     |
| `organisms/` | Secciones completas de la página                | No hacen fetch, reciben props tipadas              |

Reglas adicionales:

- **Un componente por archivo.** Nombre del archivo = nombre del componente.
- **Named exports.** `export function Button()`.
- **Props tipadas.** Los contratos de props viven en `src/components/types.ts`.
  Los tipos del dominio se infieren con `z.infer` desde `src/components/schemas.ts`.
- **Barrel exports.** Todo componente nuevo se exporta desde
  `src/components/components.ts`. Es la API pública del sistema de diseño.
- Los componentes internos usan imports directos (`../atoms/Button`) para no
  crear ciclos a través del barrel. Desde fuera del sistema, se importa del
  barrel.
- Si un prop no describe cómo se ve el componente sino qué dato es, ese prop
  pertenece al organism, no a la molecule.

Al agregar un componente: definir el nivel, escribir los props en `types.ts`,
implementarlo, exportarlo desde `components.ts`, y si es una sección nueva,
agregar su skeleton.

## Server Components por defecto

- Todo es **Server Component** salvo que necesite estado o interacción del
  navegador.
- `"use client"` va lo más cerca posible de la hoja: el componente interactivo,
  no el organism que lo contiene.
- Un Server Component **no** puede importar un Client Component que use hooks
  como `useState` sin pasar por `children`.
- Aislá el estado en la hoja más baja del árbol. El mismo dato en dos niveles
  es una fuente de verdad duplicada: elegí una.
- `src/app/page.tsx` es el orquestador: pide los datos una vez y pasa props
  tipadas a cada organism. Ningún componente consulta Supabase por su cuenta.

## Skeletons: siempre

- `src/app/error.tsx` y `src/app/loading.tsx` existen **siempre**. Son la red de
  seguridad de la UX: sin ellos, un error de datos muestra pantalla en blanco.
- Hay un skeleton por sección en `src/components/skeletons/`, todos indexados
  desde `src/components/skeletons/skeletonindex.tsx`.
- Los skeletons se usan para el primer prototipo. Después, el usuario indica
  cuándo actualizarlos: no los reescribas por initiative propia.
- `loading.tsx` consume el skeleton de página completa (`HomePageSkeleton`).

## Flujo de datos

```
src/app/page.tsx                (orquestador, server)
  └─ getSiteData(lang)          src/services/data/site.ts
       ├─ fetchFromStatic()     JSON local
       └─ fetchFromSupabase()   RPC get_site_payload(p_lang)
  └─ props tipadas
       └─ organisms/            Header, HeroSection, SkillsSection...
            └─ molecules/       NavBar, ProjectCard, Formulary...
                 └─ atoms/      Button, Title1..4, Span, Paragraph...
```

El layout lleva el estilado general: clases de `<html>` y `<body>` (fondo,
color de texto, tipografía, scrollbar, `scroll-smooth`). `page.tsx` queda lo
más simple posible: un `React.Fragment` con header → main → footer, y `main`
declara el orden de las secciones.

## Data dual

El sitio se alimenta de un único payload con dos mapas: `content` (textos
traducibles) y `metadata` (datos no traducibles). Los proyectos son dinámicos:
se detectan por el prefijo `project.` y se ordenan alfabéticamente por slug.

| Modo       | Origen                                    | Cuándo                            |
| ---------- | ----------------------------------------- | --------------------------------- |
| `static`   | JSON local en `src/services/data/static/` | Sin base de datos, prototipos, CI |
| `supabase` | RPC `get_site_payload`                    | Producción, contenido editable    |

El switch vive en `src/services/env.ts` (`resolveDataSource()`):

```bash
DATA_SOURCE=static     # fuerza el modo estático
DATA_SOURCE=supabase   # fuerza el modo Supabase
```

Sin `DATA_SOURCE`, se usa Supabase solo si hay credenciales cargadas; si no, el
template arranca con los JSON de ejemplo.

**Los dos modos devuelven exactamente la misma forma.** Por eso ningún
componente sabe de dónde salieron los datos, y cambiar de modo no toca una
sola línea de JSX. Los componentes no cambian entre modos: cambia la fuente.

Todo payload pasa por Zod antes de llegar a un componente. Si un bloque no
cumple el schema, `getSiteData` lanza un error con la key y el mensaje del
problema: falla ruidoso en vez de renderizar datos rotos.

## Variables de entorno: acceso estático

**Regla dura: el acceso a `process.env` es siempre estático.**

```ts
// Bien: Next.js puede inlinear el valor en el bundle
process.env.NEXT_PUBLIC_SUPABASE_URL;

// Mal: el bundler no puede resolverlo, llega undefined en el navegador
process.env[name];
```

Con un índice dinámico, `process.env` queda vacío en el navegador y la variable
llega como `undefined` en runtime. El síntoma típico es que falla **solo en
browser**, y muchas veces recién en un image loader.

Por eso `src/services/env.ts` expone getters, no constantes: cada getter
accede a su variable de forma estática y el error aparece en el momento del
uso, no al importar el módulo.

## Manejo de errores

- Centralizado. `src/app/error.tsx` es el punto de entrada de la UI de error.
- **Nunca** expongas `error.message` crudo al usuario: puede filtrar SQL,
  paths del sistema de archivos o estructura interna.
- Los errores de datos se loguean en el servidor (`console.error`) y al usuario
  se le muestra un mensaje genérico.
- `MissingEnvError` es el error de referencia para variables faltantes.

## Documentación del proyecto

La documentación vive en `docs/`, **dentro de la carpeta de código**.

```
docs/
  README.md        ← índice general
  graphify/        ← output del grafo (generado, no se trackea)
  <modulo>/        ← una carpeta por módulo, cada una con su README.md
```

Reglas:

- Una carpeta por módulo, cada una arrancando con un `README.md` que indexa su
  contenido.
- `docs/README.md` es el índice general: explica y linkea la documentación.
- El README raíz del proyecto es para **humanos**: propósito, objetivos,
  features, diagramas explicativos, tips rápidos.
- `.hermes.md` es para la **IA**: reglas operativas. No se mezclan.
- Nombres de archivo en `kebab-case`, **sin numeraciones ni fechas**.
- La documentación describe el estado actual del código, no la historia.
- Cambios significativos van al `CHANGELOG.md` del proyecto.

## Reglas de trabajo

1. **NO commits ni push** sin autorización explícita del usuario. Ni `git
   commit`, ni `git push`, ni `gh pr create`.
2. **NO refactorizar ni borrar código del usuario** sin consultar. Antes de
   cambiar un componente, un service o un schema: verificar el estado actual,
   preguntar qué cambiar y esperar confirmación.
3. **Reutilizar código, no reinventar la rueda.** Si el componente ya existe
   en el template o en `components/`, se reusa.
4. **No romper lo que funciona.** Patch, no rewrite.
5. **Calidad sobre velocidad**: type hints, docstrings en funciones públicas,
   nombres descriptivos, Biome limpio.
6. **TDD cuando aplique**: documentá el comportamiento esperado antes de
   escribir la implementación.
7. **Cargar las skills relevantes** al inicio de cada tarea (`nextjs-*`,
   `project-code-standards`, `motion-react`, etc.).
8. **Vault-first**: antes de investigar online, buscar en el vault.
9. **Graphify para buscar en código.** Argos indexa el vault, no el código
   fuente. Para saber qué importa qué: `jq` sobre `docs/graphify/graphify-out/graph.json`.

### Comandos

```bash
~/.bun/bin/bun install        # o `bun install` si está en el PATH
~/.bun/bin/bun run dev        # servidor de desarrollo
~/.bun/bin/bun run lint       # biome check
~/.bun/bin/bun run build      # build de producción
~/.bun/bin/bunx tsc --noEmit  # typecheck
```

Antes de dar por terminada una tarea, los cuatro tienen que pasar:
`tsc --noEmit` sin errores, `bun run lint` limpio, `bun run build` OK, y el
dev server respondiendo con contenido renderizado.
